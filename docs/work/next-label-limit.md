## 目的
エージェントが回答の末尾に書く `next` ブロックのうち、ラベル（`label`）が 30 文字を超えたカードは、パネルが黙って捨てる。直近の回答でこれが起き、カードが出なかった。
出典: 端末からの入力（会話 9e2f38e8、2026-11-22 11:17、発言 538a3ee3）と、端末からの入力（会話 9e2f38e8、2026-11-22 11:22、発言 ca903409）。
要旨（Claude の要約）: 上限を機械的に守らせたい。そのうえで、30 文字がパネルの幅から見て妥当かを実測し、上限を広げられるかを調べる。

## いまの方針
上限は 30 のまま、上限を超えたラベルのカードは、捨てずに 29 文字と「…」に切り詰めて出す（リーダーが選んだ）。エージェントへの指示文の「ラベルは 30 文字まで」は変えない。

## 判明した事実
- 30（ラベル）、300（プロンプト）、80（理由）、3（件数）は、上流の agent-status-panel（同じ選択肢を iPhone に出すアプリ）の規則に合わせたもの。`src/next-actions.mjs` の冒頭に「規則は agent-status-panel に合わせる」とあり、README にも同じ約束がある。数字の理由（ボタンの幅なのか、目安なのか）は、上流の README とコードのどちらにも書かれていない。
- 規則を満たさないカードは、上流も plugin も、ブロック全体ではなく 1 枚ずつ捨てる（`isSuggestion` で絞る）。理由（`reason`）だけは、規則を外れても切り詰めて残す。
- カードのラベルのスタイル（`panel/style.css`）は、折り返しの制限も省略表示も無く、長いラベルは折り返してカードが縦に伸びる。プロンプトは 3 行で切り、理由は切らない。
- 実機のパネルの幅は 349 CSS ピクセル（`orca plugin shot` の撮影、2026-11-22。幅はリーダーがサイドバーをどう広げているかで変わる）。実機のパネルは Windows の `Yu Gothic UI`（かなが比例幅で、13px で 1 文字が約 11px）で描画される。確かめ方: 同じ文字列の幅が、`Yu Gothic UI` の計測値（275.6px）と実機の撮影画像（約 276px）で一致した。
- 実機のフォント（`Segoe UI`、`Yu Gothic UI`）で、パネルと同じ CSS を使って、ラベルの長さごとの行数を測った（WSL 側の Chromium に Windows のフォントを使わせた。折り返しは、実機の撮影画像の目標、タスクの行数と一致することで較正した）。ラベルの行数（カード全体の高さ）:

  | 幅 | 日本語のラベル | 英数字の多いラベル |
  |---|---|---|
  | 349px（実機） | 23 文字まで 1 行（133px）、30〜60 文字は 2 行（153px） | 40 文字まで 1 行、50〜60 文字は 2 行 |
  | 280px（狭いとき） | 12 文字は 1 行、23〜40 文字は 2 行、50〜60 文字は 3 行（172px） | 30 文字まで 1 行、40〜60 文字は 2 行 |
  | 440px（広いとき） | 35 文字まで 1 行（99px）、40〜60 文字は 2 行（118px） | 50 文字まで 1 行、60 文字は 2 行 |

  1 行増えるごとにカードは約 20px 伸びる。カードの高さの大半は、理由（12px、折り返す）とプロンプト（最大 3 行）が占める。
- 結論: 30 文字は、パネルの幅から決まる値ではない。実機の幅（349px）で、日本語 60 文字までが 2 行に収まるので、上限を 40 や 60 にしても、パネルの表示は壊れない（1 行増えるだけ）。狭いとき（280px）は、40 文字までなら 2 行。
- 直近の回答 3 回でカードが出なかったのは、ラベルが 35、35、39 文字で、上限を超えたため（回答の `next` ブロックを plugin の解析に通して確認）。

### 2026-11-22 採用: 上限は 30 のまま、上限を超えたラベルは捨てずに 29 文字と「…」に切り詰める
- 出どころ: 端末からの入力（会話 9e2f38e8、2026-11-22 11:38、発言 2a968fdf）
- 要旨（Claude の要約）: 利用しているのは Android で、iPhone のアプリの制約は外してよい。提示した案のうち、plugin がラベルを切り詰める案を選んだ。
- 理由: カードが消える失敗を、見た目だけの失敗に変えられる（理由が切り詰めで残るのと同じ扱い）。パネルの幅は上限の理由にならず、実機の幅で日本語 60 文字までが 2 行に収まる。
- 状態: 有効

### 2026-11-22 棄却: 全セッションの Stop フックで、上限を超えた next ブロックを書き直させる
- 理由: リーダーが切り詰めの案だけを選んだ。この案の根拠は iPhone のアプリが切り詰めを持たず、カードが消えることだったが、その制約は外してよいと示された。
- 状態: 有効

### 2026-11-22 棄却: 上限を 40 に広げる
- 理由: リーダーが切り詰めの案を選び、理由の提示はない。

## 済んだこと
- 上限の由来を、コードと上流の README で確かめた。
- 実機のパネルの幅と、描画のフォントを実測し、ラベルの長さごとの行数を測った。
- 30 文字を超えるラベルを切り詰める修正を、テスト先行で入れた。`parseSuggestions` が、上限を超えたラベルを 29 文字と「…」にして、カードを残す。README の規則の記述も直した。この会話の最終回答のうち、これまで捨てられていた 3 回分（ラベル 35、35、39 文字）のブロックが、修正後の解析でカードになることを確かめた。
- コードレビュー（a3147ec から 6de7b5a の範囲。切り詰めと、確認間隔の設定の移し替え）を受けた。設計の前提（ラベルは表示だけで、どこでも照合や ID に使われない。切り詰めたラベルは、以前に表示を許していた長さを超えない）を崩す指摘はなく、「取り込んでよい」の判定だった。反映したのは、ファイル冒頭のコメントの食い違いと、サロゲートペアの境目と、末尾が「…」のラベルを固定するテスト。反映しなかったのは、絵文字の結合や旗の途中で切れること、切れ目が空白の直後のとき「…」の前に空白が残ること（まれで見た目だけ。既存の `shorten` と同じ性質）。このレビューの範囲外の、この会話より前の WSL 対応のコミットは、この会話ではレビューしていない。

- 2026-11-22 に、切り詰めの修正（2abba42）とレビューの反映（16b8bdc）が fork の `wsl-host`（bd7af1a）に入っていることを確かめ、記録を済みにした。作業用のワークツリーとブランチは消した。
