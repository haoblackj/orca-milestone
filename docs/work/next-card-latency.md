## 目的
Orca の Milestone パネルで、エージェントが回答の末尾に `next` のコードブロックを書いても、カードがすぐには出ない。どこで何秒待っているかを実測し、原因を直す。
依頼の出典: 別の Claude セッションからの引き継ぎ（SendMessage、未確認）。引き継ぎは、リーダーの「別のセッションで Milestone の遅れを調べて」を伝えている。この文は会話の記録では、Claude が出した候補を選んだ文としてしか見つからず、リーダーの原文としては確かめられていない。
要旨（Claude の要約）: 遅れの原因を実測して直す。実装はワークツリー、TDD、コードレビューを通す。Windows の Orca への読み込み直し、fork への push、既定ブランチへの取り込みはリーダーの承認を取ってから。

## いまの方針
原因は確定した（下の事実）。Windows の Orca は WSL のエージェントの状態変化をプラグインへ知らせないので、カードは 30 秒ごとの定期の更新まで出ない。イベントに頼らず、エージェントが作業中のあいだは短い間隔で Orca に聞き直す。失敗するテストを先に書いて直し、コードレビューを通してから、読み込み直しの承認を取る。

## 判明した事実
- Orca が done にする時刻は、Claude の transcript の最後の assistant 発言から約 0.1 秒後で、Orca 側の検知は遅れていない（`orca worktree ps` の `stateStartedAt` と transcript の時刻を 2026-11-22 に比較）。
- 実機（Windows の Orca から WSL のエージェント）では、プラグインの `agent.status.changed` が一度も届かない。計測版を読み込んだ後、試験用の Claude を working から done まで動かしたが、ログの `event agent.status.changed` は 0 件だった（2026-11-22、`orca.exe plugin logs`）。README の「イベントで知る」前提が成り立たない。
- そのため、カードを作り直す `orca worktree ps` の取り直しは、`workspace.changed`（フォーカスの変化）と 30 秒ごとの定期（`SYNC_MS`）でしか起きない。試験用の Claude の done は t=1795308787304、次の取り直しは定期の t=1795308797046（9.7 秒後）で、完了は t=1795308800037（12.7 秒後）だった。定期は 30 秒間隔なので、遅れは平均 15 秒、最大 30 秒に更新の所要時間が加わる。
- 1 回の更新は実機で約 2〜2.7 秒かかる（ログの `orca=` と `sessions=` の合計）。当初は `orca=` を `worktree ps` 単体の時間と読んだが、誤りで、内訳は下の実測のとおり（`worktree ps` は約 0.5 秒）。
- 以前のログに、`--environment` 付きの `worktree ps` が `remote_runtime_unavailable` で失敗した行がある（2026-11-21 23:53Z）。失敗した更新は次の契機まで待つ。
- `workspace.changed` は実機で十数秒おきに届き、そのたびに更新が走る。
- Claude のセッションファイル（`~/.claude/sessions/<pid>.json`）の `status` が idle になる時刻は、Orca の done より 1.7〜2.2 秒遅い（4 件を実測）。表示までの見込みは、2 秒の確認間隔と約 2〜2.7 秒の更新を足した 4〜7 秒で、以前の最大 30 秒より短い。
- 修正版を実機に読み込んで測り直した（2026-11-22、b0f80a3）。試験用の Claude の最終的な done が t=1795309767581、見張りが idle を見つけて Orca に聞き直し始めたのが t=1795309769356（Windows と WSL の時計のずれが 0.1 秒ほどある）、その更新の完了が t=1795309773135。done から、done の中身（`lastAssistantMessage`）を取り込んだ更新の完了まで 5.55 秒で、修正前の 12.7 秒（最大 30 秒）の半分以下になった。
- 見張りの 1 回の所要時間は、実機の共有越しで 83〜118 ms（変化を見つけた回のログ）。
- 訂正: ログの `orca=` は `orca worktree ps` 単体ではなく、`readWorkspaces` 全体（ps と、その後の transcript や sessions の読み出し）の時間だった。上の「`orca worktree ps --environment` が 1.2〜2.1 秒」と、以前の README 風の説明は、この意味で読み替える。
- 試験では、同じワークスペースに試験用の Claude と作業中の Claude が二つ動いていたため、パネルに次の作業のカードは出ない（カードはエージェントが一つのときだけ出る）。カードがパネルに映った時刻は測っていない。測ったのは、ワーカーが done の回答を取り込むまで。
- Orca が試験用のセッションに付けた最初の done（起動直後、プロンプトを入れる前）を完了と取り違えやすい。最終的な done は、`lastAssistantMessage` に回答が入った時刻を見る。
- 同じ sessionId のファイルが 15 組ある（186 ファイル中、生きているのは 28 件、`status` を持たないものが 67 件）。再開したセッションは前のプロセスのファイルを残す。

- 更新の内訳の実測（2026-11-22、Orca 同梱の Node を `ELECTRON_RUN_AS_NODE=1` でワーカーと同じ条件に動かし、`readWorkspaces` の各部を計時。4 回）:
  - `readWorkspaces` 全体は 2.17〜2.49 秒。うち `orca.exe worktree ps --environment` は 0.46〜0.53 秒で、`readTurnEnded`（作業中のエージェントがあるワークスペースごとに 1 回、このときは 2 回）が合計 1.71〜1.99 秒。これで全体の約 8 割。
  - `readTurnEnded` 1 回は 0.77〜0.81 秒で、その 0.64〜0.67 秒が `readRunningSessions`（`~/.claude/sessions` の 186 ファイルを、一つずつ読み、一つずつ `/proc/<pid>` を stat する）。transcript を探す時間は 7〜9 ms、末尾を読む時間は残りの約 0.1 秒。
  - 更新 1 回のうち、同じフォルダーの読みは 3 回走る（`allSessions` の `readRunningSessionIds` が 1 回、`readTurnEnded` が作業中のワークスペースの数だけ）。1 回 0.64〜0.74 秒なので、更新 2.9 秒（ps 0.5 + readTurnEnded 1.7 + 一覧 0.7）のうち約 2.1 秒がこの読み。
  - 共有越しの部品（186 ファイル）: 一つずつ `readFile` が 555〜634 ms、同時にすると 163〜211 ms。`stat` は一つずつ 271〜308 ms、同時に 79〜87 ms。`/proc/<pid>` の stat は一つずつ 89〜107 ms、同時に 23〜29 ms。`readdir` は 2 ms。
  - WSL から `orca.exe worktree ps --environment` を打つと 0.59 秒で安定する。`--limit 1` にしても 0.58 秒で縮まず、`--since 1d` は 0.72 秒でむしろ遅い（出力の大きさは効かない）。
  - 別経路 `wsl.exe -d Ubuntu -e <WSL の orca> worktree ps` は Windows の Node から 0.24〜0.39 秒で、`orca.exe --environment` の 0.48〜0.76 秒より約 0.25 秒速い。ただし distro 名と WSL 側の CLI のパスを決め打ちにする。
- 縮める修正の効果（2026-11-22、同じ条件の計測で修正前後を比較。キャッシュが温まった 2 回目以降）: セッション一覧 0.66 秒から 0.10 秒、`readTurnEnded` 1 回 0.82〜0.95 秒から 0.30 秒、`readWorkspaces` 全体（作業中のエージェントが一つのとき）1.3〜1.4 秒から 0.75〜0.79 秒。見積もり（一覧 1 回 0.12 秒、更新 2.9 秒から 1.1 秒）と合っている。`readTurnEnded` に残る 0.3 秒は、一覧 0.1 秒と transcript の末尾の読み 0.13 秒ほど。

## 判断の経緯
### 2026-11-22 採用: 実機の計測用ログを足してから直す
- 出どころ: Claude の判断
- 理由: 遅れの大きさを決めるのは、Windows の Orca が WSL のエージェントの状態変化をプラグインへ知らせるかどうかで、WSL のコマンドからは見えない。推測で直さず、イベントの到着と各区間の時間をログに出して確かめる。
- 状態: 有効

### 2026-11-22 採用: 計測版を Windows の Orca に読み込み直す
- 出どころ: 端末からの入力（このセッションでリーダーが承認。出典の発言 ID は未確認）
- 要旨（Claude の要約）: 計測ログ入りの版（milestone-latency）を `orca.exe plugin dev reload` で読み込み直し、ターンを一回終えてログを読み、遅れる区間を特定する。
- 理由: 上の判断のとおり。
- 状態: 有効（計測は済んだ）

### 2026-11-22 棄却: 作業中のあいだだけ Orca への聞き直しの間隔を短くする
- 出どころ: Claude の判断（技術の選択）
- 理由: 作業中かどうかは取り直さないと分からず、30 秒より短いターンは作業中を見ないまま終わる。短い返事ほどカードが遅れる。
- 状態: 有効

### 2026-11-22 採用: Claude のセッションファイルの busy / idle の変化で Orca に聞き直す
- 出どころ: Claude の判断（技術の選択）
- 理由: Claude は `~/.claude/sessions/<pid>.json` の `status`（busy / idle）と `statusUpdatedAt` を、ターンの始まりと終わりで更新する。WSL の共有越しに読む 1 回は小さな JSON の読み出しだけで、1 回 2 秒の更新を走らせ続けるより軽い。変わったときだけ `orca worktree ps` を取り直すので、ターンの終わりから、2 秒の確認の間隔と更新の所要時間（約 2〜2.7 秒）で表示が出る。Orca が `agent.status.changed` を送る環境（macOS など）には、設定しない限り効かない（WSL のときだけ 2 秒間隔で有効）。
- 状態: 有効

### 2026-11-22 採用: レビューの指摘のうち、ファイル名で持つ、更新時刻で読み直す、トレースを切り替え式にする、見張りを例外で止めない
- 出どころ: Claude の判断（コードレビューの指摘を、実データで確かめて受けた）
- 理由: 重複した sessionId は実データで 15 組あり、同じ ID の生きたファイルが二つある組もあった（186 ファイル中、生きているのは 28 件）。ID をキーにすると、後ろに並んだ古いファイルが生きたファイルを隠す。更新時刻が変わったファイルだけ読めば、共有越しの読み出しが減る（手元の実測は初回 72 ms、以降 5〜10 ms）。トレースの行は上流の既定の動作を変えるので、WSL のときだけ付ける。
- 状態: 有効

### 2026-11-22 棄却: busy から idle に変わった後に、もう一度 Orca に聞き直す
- 出どころ: Claude の判断（レビューの指摘への返答）
- 理由: セッションの idle は Orca の done より 1.7〜2.2 秒後に記録される（4 件の実測）。idle を見て取り直す時点で Orca はすでに done なので、取り損なう競合は起きない。
- 状態: 有効

### 2026-11-22 採用: fork に push してから、セッション読みを縮める
- 出どころ: 端末からの入力（会話 9e2f38e8、2026-11-22 10:19、発言 3aee94a4）
- 要旨（Claude の要約）: 先に `wsl-host` を fork に push し、そのあとで更新の所要時間を縮める。
- 理由: 提示した縮める案（読みの共通化）と、push の順序を、リーダーが決めた（理由の言及なし）。
- 状態: 有効

### 2026-11-22 採用: セッションファイルの読みを更新時刻とサイズで読み直す共通のキャッシュにする
- 出どころ: Claude の判断（技術の選択）
- 理由: 共有越しでは 1 ファイル 3.3 ms で、186 ファイルを一つずつ読むと 0.64 秒、同時に読むと 4 倍速い。同じフォルダーの読みが更新 1 回で 3 回走っていた。ファイル名キーのキャッシュに三つの読み関数を乗せ、pid の生死は毎回確かめる。同じ時刻とサイズで中身だけ変わった書き込みは見逃すが、Claude の状態の書き込みは数秒おきで、見逃す窓は 1〜10 ミリ秒の時刻の粒度に限られる（レビューで確認。共有越しの時刻の精度は未測定）。
- 状態: 有効

## いまの作業
`sessions-read` ブランチで、読みの共通化をコードレビューまで終えた（62f30f7 と、指摘の反映のコミット。テスト 111 件）。`wsl-host` は push 済み（5a1dd83）。実機に読み込み直す承認を待っている。

## 済んだこと
- 経路をコードで追い、Orca の done の検知が速いことを確かめた。
- 計測ログ入りの版を実機に読み込み、遅れの原因（イベントが届かず、30 秒の定期に頼っている）を確定した（1a9a2b3）。ローカルの `wsl-host` はこのコミットまで進めてある。
- セッションの状態を見張る修正をテスト先行で入れ、コードレビューを受けて直し、実機で測り直した。fork の `wsl-host` に push した（5a1dd83、履歴の書き手は noreply、記録は公開向けに一般化）。
- セッションファイルの読みの共通化を、テスト先行でコードレビューまで終えた（`sessions-read`、実機と同じ条件の計測で `readWorkspaces` が 1.3〜1.4 秒から 0.75〜0.79 秒）。

## 残っていること
- 共通化の修正を実機に読み込み、カードが出るまでの時間を測り直す（読み込み直しの承認が要る）。
- 修正を fork に push する承認、既定ブランチへの取り込みの承認。
- パネルにカードが映るまでの目視（エージェントが一つだけのワークスペースで）。

## 次に Claude がすること
- リーダーが承認したら、`wsl-host` を `sessions-read` まで進め、`orca.exe plugin dev reload` で読み込み直し、試験用の Claude で done から更新の完了までを測り直す。
